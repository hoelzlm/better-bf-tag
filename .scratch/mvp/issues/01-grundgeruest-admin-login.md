## Agent Brief

**Category:** enhancement
**Summary:** Lauffähiges Grundgerüst des Monorepos mit Backend, Web-App und Test-Infrastruktur; ein Administrator kann sich im Web anmelden.

**Current behavior:**
Das Repo enthält nur Dokumentation (`docs/`, `CONTEXT.md`, ADRs) und leere Ordner mit READMEs für Backend, Apps, Pakete und Infra. Es gibt keinen Code, keine Tests und keine CI.

**Desired behavior:**
- Das Backend (Node.js 24 LTS, TypeScript, Fastify) läuft lokal per Docker Compose mit PostgreSQL 17. Datenbank-Migrationen (Drizzle) laufen beim Start, ein Health-Endpunkt meldet auch den Zustand der Datenbank.
- Fehlt ein Administrator, legt das Backend beim Start einen aus der Server-Konfiguration an (Bootstrap-Benutzername und -Passwort). Die Person bekommt Personentyp Betreuer und Berechtigung Administrator.
- Web-Login mit Benutzername und Passwort (Argon2id). Das Access-Token ist ein JWT mit 15 Minuten Laufzeit (`sub`, `permission`). Das Refresh-Token liegt als HttpOnly-Cookie vor und wird bei jedem Refresh rotiert. Logout widerruft es. Die Auth-Endpunkte sind rate-limitiert. Fehler kommen im einheitlichen Format `{ error: { code, message } }`.
- Validierung und Schemas laufen über zod. Die OpenAPI-Spezifikation wird daraus erzeugt und ins Repo committet. Ein Root-Befehl generiert daraus den Dart-Client (openapi-generator, dart-dio).
- Das Flutter-Monorepo ist ein Pub Workspace mit drei Teilen: einer Web-App mit den Routen `/admin` und `/monitor` (go_router, Riverpod), einem gemeinsamen Dart-Paket und dem generierten API-Client. Die Web-App zeigt einen Login-Screen und danach eine leere Lage. `/monitor` darf ein Platzhalter sein.
- Die Test-Infrastruktur testet das Backend als Black Box über HTTP, gegen eine echte PostgreSQL im Testcontainer. Beim Start lassen sich zwei Abhängigkeiten austauschen: eine Zeitquelle (`Clock`), die in den Tests steuerbar ist, und ein Push-Versand (`PushSender`), der im Test als Fake alle Pushes aufzeichnet. Für den Push-Versand reicht hier nur die Schnittstelle, die echten Anbieter kommen in Ticket 09.
- Root-Befehle über `just` oder `make`: `dev`, `test`, `gen-api`.
- CI über GitHub Actions: Backend-Tests sowie Flutter `analyze` und `build web`, gefiltert nach geänderten Pfaden.

**Key interfaces:**
- `Clock` – liefert die aktuelle Zeit. Alle zeitabhängigen Module nutzen ausschließlich diese Schnittstelle.
- `PushSender` – „sende Push an Geräte“. Die Implementierung wird beim Start eingeschleust. Die Tests verwenden den aufzeichnenden Fake.
- Auth-Endpunkte unter `/api/v1/auth`: `login`, `refresh`, `logout`. Health unter `/api/v1/health`.
- Tabelle `person` mit den Spalten aus docs/03-datenmodell.md, mindestens den für den Login nötigen. Die Berechtigung Administrator ist nur mit dem Personentyp Betreuer zulässig (Constraint in der Datenbank).
- Begriffe aus `CONTEXT.md` verwenden, z. B. Person, Berechtigung, Personentyp, nicht „User“ oder „Role“.

**Acceptance criteria:**
- [ ] `docker compose up` startet Backend und PostgreSQL lokal, der Health-Endpunkt antwortet mit 200
- [ ] Beim ersten Start existiert der Bootstrap-Administrator, beim zweiten Start wird kein weiterer angelegt
- [ ] Tests: Login mit richtigem bzw. falschem Passwort, Refresh rotiert das Token, ein altes Refresh-Token wird abgelehnt, Logout widerruft
- [ ] Test: Ein Access-Token ist nach 15 Minuten abgelaufen; die steuerbare Uhr ersetzt dabei das Warten
- [ ] Test: Rate-Limit auf Login greift
- [ ] Test: Das Constraint zwischen Administrator und Betreuer wird erzwungen
- [ ] Die OpenAPI-Datei ist erzeugt, und `gen-api` erzeugt einen kompilierbaren Dart-Client
- [ ] Die Web-App meldet sich gegen das lokale Backend an und zeigt die leere Lage; ein ungültiger Login zeigt eine Fehlermeldung
- [ ] CI ist grün für Backend und Flutter
